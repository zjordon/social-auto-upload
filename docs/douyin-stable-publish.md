# 抖音稳定发布：浏览器 Profile 整合复盘

> 2026-11-05 ~ 2026-11-07 · 三天排查与修复的完整记录
> 结论先行：抖音上传风控的核心信号是**浏览器档案（profile）的持续性**，不是自动化协议本身。
> 修复后从「9 小时空转」到「40 秒端到端」。

## 一、背景与目标

目标：用 `sau douyin upload-video --draft` 一条命令在本机稳定发抖音视频草稿（标题/描述/声明/合集/双封面全参数）。

改造前该项目抖音流程的默认形态：每次运行用 patchright **新开一个一次性临时浏览器**（临时 profile + 注入登录 cookie），跑完即弃。

## 二、问题现象

- 3.2MB 的视频上传磨 2 分钟后页面报「上传失败」，自动重传后进度条卡死；
- 换真 Chrome 二进制（`LOCAL_CHROME_PATH`）症状相同；
- 卡死时网络层表现：五个上传端点的 POST 发出后**服务端零响应**，60 秒后页面 JS 自行超时中止；
- 登录、打开页面、填表等一切正常——只有上传传输被掐。

## 三、排查时间线与对照实验

按时间顺序的关键实验（全部同一台机器、同一账号、同一个 3.2MB 文件）：

| # | 实验 | 结果 | 排除了什么 |
|---|------|------|-----------|
| 1 | 内置 chromium 145 临时 profile | ❌ 黑洞 | — |
| 2 | 真 Chrome 156 临时 profile | ❌ 同样黑洞 | 浏览器二进制 |
| 3 | 手动在日常 Chrome 上传 | ✅ 秒传 | 网络、CDN、账号基础状态、文件本身 |
| 4 | **持久化 profile**（patchright，`launch_persistent_context`） | ✅ **2-4 秒** | **一次性 profile = 根因** |
| 5 | #4 + 注入 stealth.min.js | ✅ 56 秒（变慢不死） | stealth 脚本 |
| 6 | #4 + 先跑 cookie_auth 临时校验 | ✅ 4 秒 | cookie 预校验 |
| 7 | #4 + geolocation 权限 | ✅ 4 秒 | 权限差异 |
| 8 | chrome-devtools MCP（真 Chrome + 多年持久 profile） | ✅ 秒传 | CDP 协议本身（它也是 CDP 驱动） |

补充证据：

- 网络探测：上传 CDN（`tos-lq-x.bytedancevod.com`）IPv4/IPv6 双栈全通（HTTP 204），**同一个端点**在临时 profile 会话下黑洞、持久 profile 会话下秒回 200——服务端按会话风险**选择性响应**；
- 上游 issue [#224](https://github.com/dreammis/social-auto-upload/issues/224) 独立佐证：抖音/快手可识别 playwright 启动的浏览器特征，「即使 --headed 也常被识别」，其验证的修复方向正是 CDP 接管本地真实 Chrome。

### 账号层风控（第二层）

排查期间同账号约 24 小时内 ~10 次上传测试，触发**滚动窗口频率限流**：修复后的方法也会被挂起（表现为页面停在「文件解析中 0%」），且页面内部持续重试会刷新窗口，最长空转 9.3 小时直至日级计数重置。约 10 小时无尝试后自然衰减，单次上传即恢复正常。

**结论：风控是两层的——会话/设备层看 profile 持续性（已修复），账号行为层看上传频率密度（靠使用习惯规避：单日别反复测试上传）。**

## 四、修复中被一并发现的三个程序 Bug

1. **上传完成检测器过期**：`[class^="long-card"]` 是旧版页面 DOM；新版「重新上传」在右侧预览面板。且文本兜底若用 `get_by_text(..., exact=True)` 会因元素文本含不可见字符**永不命中**——上传已成功也无限空转。
2. **草稿按钮文案与成功判定错**：按钮实为「暂存离开」（不同页面版本也叫「存草稿」），点击后跳转 `content/upload`（非发布流程等待的 `content/manage`）。
3. **上传等待循环无超时、失败重试无上限**：风控挂起时 9 小时空转；已加 `DOUYIN_UPLOAD_TIMEOUT`（默认 900s）超时报错 + 重试 3 次上限。

## 五、方案设计：双模式浏览器获取

`DouYinBaseUploader._acquire_context()`（`uploader/douyin_uploader/main.py`）统一两个模式：

| 模式 | 触发 | 行为 | 适用 |
|------|------|------|------|
| **CDP 接管**（推荐） | `--cdp-url http://127.0.0.1:9223` 或环境变量 `SAU_DOUYIN_CDP_URL` | `connect_over_cdp` 接到常驻浏览器，**只管理自己新开的标签页**（结束只关该页）；不关用户浏览器、不注入 stealth、不种 cookie——常驻档案的信任基线正是要复用的东西 | 已有常驻发布浏览器的用户（信任基线最高） |
| **自有持久化 profile** | 未给 cdp-url | `launch_persistent_context` 固定档案 `~/.social-auto-upload/browser-profiles/douyin_<account>/`，首次从 cookie 文件种入登录态，此后档案即登录态载体 | 无常驻浏览器的场景（档案会随使用时长积累信任） |

配套加固：

- **登录校验内移**：上传流程在已获取的上下文里检测登录态（打开上传页看是否被踢到登录页），删除了原先每次上传用全新临时浏览器跑 `cookie_auth` 的两处预检——「陌生设备反复读 cookie」本身就是风控信号；
- **网络诊断**：上传端点（`bytedancevod` / `/upload/` 路径）的请求与**全状态码响应**记入日志（排查期最大的盲区是 200 响应不可见，导致「传输死」与「检测器瞎」不可分辨）；过滤 `mcs.snssdk.com` 遥测与 `blob:` 中止噪音；
- **合集选择器**：宽松文本兜底 + miss 时 dump 下拉 DOM 片段（选择器盲改是本次 bug 的教训之一，修选择器必须带证据）。

## 六、使用方法

前提（CDP 模式）：常驻浏览器带调试端口运行，例：

```
chrome.exe --remote-debugging-port=9223 <你的日常 profile 或独立 profile>
```

发草稿：

```powershell
sau douyin upload-video --account creator --file <视频> `
    --title <标题> --desc <描述> `
    --collection <合集名> --declaration "无需添加自主声明" `
    --thumbnail-landscape <横封面> --thumbnail-portrait <竖封面> `
    --draft --cdp-url http://127.0.0.1:9223
```

- 环境变量 `$env:SAU_DOUYIN_CDP_URL="http://127.0.0.1:9223"` 设一次后可省 `--cdp-url`；
- 首次使用某账号先 `sau douyin login --account <name>` 扫码一次（持久化 profile 模式必须；CDP 模式下常驻浏览器已登录即可）；
- 去掉 `--draft` 为直接发布；`--schedule "yyyy-MM-dd HH:mm"` 为定时发布。

## 九、经验与教训

1. **同日别反复测试真实上传**——账号层频率限流的代价是数小时到一天的通道不稳，排查期约 10 次测试换来 9 小时挂起。能用「打开页面不上传」的冒烟就用冒烟。
2. **日志要有全状态码**——只记 ≥400 的响应日志让「上传成功但检测器失明」和「传输真死」长得一模一样，浪费了一整轮排查。
3. **修选择器必须带证据**——本次两个 bug（`long-card` 过期、`exact=True` 失明）都是选择器与页面脱节的产物；盲改选择器只是把今天的错换成明天的错。miss 时 dump DOM 是低成本高收益的保险。
4. **循环必须有终点**——自动化流程里的 `while True` 配上外部不可控的服务端行为，等于把超时策略交给对手；超时 + 重试上限 + 可行动的报错文案是底线。
5. **对照实验单变量**——「换浏览器」「加 stealth」「查网络」都是整包变量的猜测；真正破局的是把变量一个个拆开（同库同机同文件，只动 profile 持续性）。
